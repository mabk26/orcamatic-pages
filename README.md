# Orcamatic website

The public website for **[orcamatic.com](https://orcamatic.com)** — plain HTML, CSS
and JavaScript. No build step, no dependencies, no backend, no API keys.

## Layout

The website **is** the repository root. Every file here is published except
`README.md`, `LICENSE`, `.gitignore`, `docs/`, `tools/` and `.github/`, which the
deployment workflow filters out — so notes and asset builders can live in the repo
without being served.

```
index.html            Homepage
404.html              Not-found page
CNAME                 Custom domain: orcamatic.com
.nojekyll             Tells GitHub Pages to serve files as-is
robots.txt            Crawler rules
sitemap.xml           Page list for search engines
site.webmanifest      Installable app metadata
assets/               site.css, site.js, icons, fonts, og-image.jpg
tools/                build-og-image.py, prepare-screenshots.py (store assets)
docs/                 website-audit.md (research + backlog), PHASES.md (execution plan),
                        website-review.md (post-mortem of a broken-looking deploy)
about/  pricing/  products/  blog/  legal pages (privacy, terms, refund)
templates/        Template library index + three written-out workflow templates
guides/first-workflow/   Five-step quickstart
security/        Permissions, data flow and store disclosures
```

| Path | Purpose |
| --- | --- |
| `index.html` | Homepage |
| `assets/site.css` | Shared responsive styling, including the scroll-driven section reveal |
| `assets/site.js` | Dependency-free mobile menu, year stamp, screenshot retry and fallback |
| `templates/` | Workflow templates: steps written out for jobs the extension does today |
| `security/` | Every permission with its reason, plus where each kind of data lives |
| `guides/first-workflow/` | Quickstart: five steps and the five failure modes worth knowing |
| `assets/og-image.jpg` | Social share card, generated by `tools/build-og-image.py` |
| `CNAME` | Production domain — also set it in **Settings → Pages** |
| `sitemap.xml` / `robots.txt` | Search-engine discovery |
| `404.html` | Friendly GitHub Pages not-found page |

## Imagery rules

Product imagery on this site is **real**: the hero and the gallery show the screenshots from the
ORCA listing on the Chrome Web Store. Do not replace them with generated or mock-up art — a
rendered "screenshot" with invented UI text is instantly recognisable and it misrepresents the
extension.

Four conventions keep that honest, and the checker enforces the last three:

- The pages hot-link the store images from `https://lh3.googleusercontent.com`, and every page's
  `Content-Security-Policy` allows exactly that host under `img-src`. If you add imagery, add it
  to the CSP of every page (the meta tag is repeated per document).
- Ask the CDN for **one width** (`=w1024`), never a box (`=s1280-w1280-h800`). A box makes Google
  crop the source to that ratio, which cuts captions and button labels off a tile that is any
  other shape. Pick the width from where the image is displayed: the hero slot is ~505px and the
  gallery ~570px, so `=w1024` and `=w1152` at 2x. A 1280px raster squeezed into a 279px column is
  unreadable *and* slower than the same tile requested at 640px.
- Every frame reserves its own `aspect-ratio: 8 / 5` (the store tile ratio) and the image covers
  it, so a tile never has to stretch to fit its slot and the layout cannot jump while loading.
- Each image sits inside `[data-shot]`. `assets/site.js` retries a failed load once, then falls
  back to a note inside the same reserved frame; a gallery tile that cannot be shown is dropped
  by CSS. A CDN problem therefore costs a sentence, not the column.

For production it is better to serve the images yourself. Save the five screenshots from the
listing into `assets/screenshots/` (`orca-1.png` … `orca-5.png`), then replace the remote URLs in
`index.html`, `products/index.html` and `about/index.html` with the local paths and drop
`https://lh3.googleusercontent.com` from the CSP.

### Regenerating the social card

`assets/og-image.jpg` is drawn from the copy and the self-hosted fonts in this repository, so it
can be rebuilt when the wording changes:

```bash
python3 -m venv .venv && .venv/bin/pip install pillow fonttools brotli
.venv/bin/python tools/build-og-image.py
```

The script is a one-off asset build; the site itself still needs no build step.

## Publishing

Deployment is automatic: `.github/workflows/deploy-github-pages.yml` packages the
site and publishes it on every push to `main`. Pull requests build the package
without publishing. A manual run also only publishes when `main` is selected.

### One-time GitHub settings

1. **Settings → Pages → Build and deployment → Source**: **GitHub Actions**
   (do *not* choose “Deploy from a branch”).
2. **Settings → Pages → Custom domain**: enter `orcamatic.com` and save.
   With the Actions workflow, the `CNAME` file alone does not configure the domain.
3. Open **Actions → Deploy Orcamatic site to GitHub Pages → Run workflow** on `main`
   if the first run happened before Pages was enabled.
4. Once DNS and the certificate check pass, enable **Enforce HTTPS**.
5. If GitHub offers a domain-verification TXT record, add it — it stops another
   Pages site from claiming the domain.

> The pages use root-relative URLs (`/assets/site.css`) and canonical URLs on
> `https://orcamatic.com`. They expect the custom domain to be the site root, not
> the `/orcamatic-pages/` project path.

records change. **Leave email records (MX, DKIM, SPF) untouched** if you use email
on this domain.

## Editing the site

Change the HTML/CSS files at the root, merge to `main`, and the site goes live
within a minute or so. There is nothing to rebuild.

Preview locally from the repository root:

```bash
python3 -m http.server 4173 --bind 0.0.0.0
# open http://localhost:4173
```

Because links are root-relative, always serve from the repository root rather than
opening the files directly.

When you add a page:

1. Create `your-page/index.html` so the URL ends with a slash.
2. Add its URL to `sitemap.xml`.
3. Link it from the header/footer navigation where it belongs.
4. Copy the page's `<meta http-equiv="Content-Security-Policy">` tag from an existing page so the
   font, image and store-CDN rules stay in sync.

Section labels stay structural: an `<h1>`/`<h2>` carries the meaning on its own, so no small
uppercase "eyebrow" line above a heading and no bullet dot in front of a label. Use `.facts`
(hairline-separated) for short lists of claims and the serif numerals in `.step-number` /
`.pillar .number` for ordered cards.

## Checking the site

There is no build, so correctness is checked instead:

```bash
python3 tools/version-assets.py         # stamp ?v=<hash> into every page after editing css/js
python3 tools/check-site.py            # errors only
python3 tools/check-site.py --strict  # advisories fail too (this is what CI runs)
```

It verifies markup balance, exactly one `<h1>` per page, the head tags every page must carry,
that every class used in HTML has a rule in `assets/site.css`, that every internal link and local
asset points at a file that exists, that the sitemap lists each page once, and that structured
data parses as JSON. It also flags inline `style` attributes and `on*=` handlers, which this site's
Content-Security-Policy blocks at runtime, the store-image rules above, and a stylesheet stamp
that does not match the file. The deploy workflow runs it with `--strict` before packaging, so a
broken page cannot reach production.

### Why the `?v=` stamp is not optional

Pages caches every file on its own URL. A deploy that lands while a browser or an edge still
holds the previous `/assets/site.css` paints the new HTML with old rules, and the page looks
destroyed - unstyled demo blocks, a gallery stacked full width, `<b>` labels glued to their
sentences - while every file in the repo is correct. It happened: see
[`docs/website-review.md`](docs/website-review.md). `tools/version-assets.py` makes the new build
a new URL, and CI fails if a page carries any other stamp, so the skew cannot recur.

## Improvement backlog and phases

`docs/website-audit.md` is the research behind the site: the scorecard, the copy proposals and
the numbers for each recommendation. `docs/PHASES.md` is the execution plan with an owner on
every line — Phase 1 is shipped in this repo, and the remaining rows are the parts that need
the extension, the store dashboard or a pricing decision. Update both when an item ships, and
record baseline metrics before changing anything so the next pass can tell improvement from noise.

### Store screenshots

`tools/prepare-screenshots.py` drives a real browser on your machine to capture the extension UI
at the exact sizes the Chrome Web Store wants (1280x800 screenshots, 440x280 promo tile,
1400x560 marquee) and exports `.jpg` beside each master:

```bash
pip install playwright pillow && playwright install chromium
python3 tools/prepare-screenshots.py --list
python3 tools/prepare-screenshots.py --extension path/to/unpacked/build --headed
```

It needs `--extension` or `--open` because no static site can show a running extension; the
homepage and the store listing both have to use the same real UI, so capture once and reuse.
